# Манифест минималистичной акторной системы

1. Полный минимализм. Ничего лишнего.
Каждый элемент системы должен иметь однозначную причину существования.
Если функциональность может быть вынесена за пределы ядра — она выносится.

2. Манифест как основание и память.
Все последующие пункты служат двум целям:
- служить основанием для написания кода (архитектурные решения выводятся из пунктов манифеста);
- восстанавливать контекст после его переполнения (достаточно прочитать манифест, чтобы продолжить разработку).

3. Среда исполнения
Язык программирования — C#, целевая платформа — .NET Core. Все решения по реализации должны использовать возможности
этой экосистемы (включая System.Threading.Channels, Task, Span, аппаратные фичи платформы), но без лишних зависимостей.

4. Изоляция и взаимодействие
Акторы параллельны по своей природе и полностью независимы друг от друга. Единственный способ взаимодействия
между акторами — асинхронный обмен сообщениями. Никакого разделяемого изменяемого состояния,
никаких прямых синхронных вызовов между акторами.

5. Очередь входящих сообщений
Каждый актор имеет очередь входящих сообщений. Сообщения обрабатываются актором строго последовательно — в том порядке,
в котором они поступили в очередь. Никакой конкурентной обработки внутри одного экземпляра актора:
в любой момент времени актор обрабатывает ровно одно сообщение.

6. Природа сообщения
Сообщение — объект, передаваемый между акторами. Может быть:
- посылкой (однонаправленный запрос);
- ответом на предыдущее сообщение;
- аккумулятором, мутирующим при последовательной передаче от актора к актору (перемещаемая изменяемая посылка).

7. Легковесность актора
Максимальное количество акторов в системе ограничено исключительно доступными ресурсами (память, процессор).
Никаких архитектурных ограничений на количество экземпляров нет.

8. Активность актора
Актор активен только в момент обработки сообщения из своей очереди. Всё остальное время он не потребляет процессорное время,
не удерживает поток и не проявляет какой-либо фоновой активности. Из этого следует: актор — это по сути
состояние + очередь сообщений. Поведение — это функция, которая выполняется при появлении сообщения и сразу засыпает.

9. Идентификация актора
Каждый актор имеет уникальный идентификатор — Guid. Идентификатор назначается при создании актора и не изменяется
на протяжении всего жизненного цикла.

10. Реестр акторов
Акторная система содержит внутренний словарь Guid → Actor. Это единственное место в системе, где хранится
прямая ссылка на экземпляр актора. Внешний код не имеет доступа к этому словарю напрямую.

11. Метод Send
Отправка сообщения актору осуществляется через публичный метод акторной системы:
    Send(message: Message)
Это единственный способ доставить сообщение актору. Метод находит актор в реестре по идентификатору и помещает сообщение
в его очередь.

12. Типизация сообщений
Сообщения строго типизированы. Тип сообщения — это всегда финальный класс (sealed), наследование сообщений запрещено.
Назначение, структура и семантика сообщения полностью определяются его типом.  Все сообщения наследуются от
абстрактного класса Message, который содержит два поля: Sender (Guid отправителя) и Receiver (Guid получателя).
Сами классы сообщений — sealed, наследование семантики запрещено.

13. Экземплярность акторной системы
Акторная система — это экземплярный объект. Никаких статических ссылок, глобального состояния или синглтонов.
В рамках одного приложения или сервиса допустимо существование нескольких независимых акторных систем.

14. Доступ актора к системе
Ссылка на акторную систему передаётся актору через конструктор при создании. Это единственный способ для актора
получить возможность отправлять сообщения другим акторам.

15. Создание акторов
Первоначальный набор акторов, образующих связи акторной системы с внешними сервисами (ввод/вывод, HTTP, очереди и т.п.),
создаётся через DI при инициализации акторной системы. Один из этих акторов является корневым родителем и выступает
фабрикой акторов прикладной задачи, создавая первый слой прикладных акторов.

Прикладные акторы создаются динамически — родитель порождает потомка через акторную систему и получает его идентификатор (Guid).
Потомок, в свою очередь, может создавать собственных потомков, формируя дерево акторов.

Системные акторы имеют константные идентификаторы (Guid), доступные как публичные свойства экземпляра акторной системы.
Это позволяет прикладным акторам отправлять сообщения системным акторам напрямую, без необходимости искать их по типу или имени.
Системные акторы могут иметь несколько реализаций, конкретная реализация выбирается через DI. Системные акторы независимы от
конкретной прикладной программы и прикладных акторов, но для каждого системного актора фиксируется набор сообщений, который
он может принимать. Системные акторы не могут посылать сообщение прикладным акторам кроме случая ответного сообщения.

Актор-родитель прикладных акторов является промежуточным звеном между системными и прикладными акторами. С одной стороны, он имеет
константный идентификатор, а с другой стороны он полностью определяется прикладными акторами.

16. Логгирование
Логгер — это простой объект (не актор), создаваемый через DI. Сохраняется как публичное свойство экземпляра акторной системы.
Все акторы вызывают методы логгера напрямую, без отправки сообщений. Выбор в пользу простого объекта сделан из
соображений эффективности: логгирование не должно проходить через очередь сообщений и поток актора.

Это важное уточнение: не всё в системе обязано быть актором. Утилитарные cross-cutting concerns остаются объектами.

17. Обработка ошибок
Ошибки не выходят за пределы актора. Каждый актор обрабатывает исключения, возникающие при обработке сообщения, внутри себя.
Если сообщение не может быть обработано, актор выводит подробности в лог и продолжает работу со следующим сообщением.

18. Аварийное завершение
Если в результате ошибки дальнейшая работа актора становится невозможной, актор вызывает метод аварийного завершения
акторной системы. Акторная система при этом рассылает специальное сообщение о завершении работы всем акторам
из внутренней таблицы акторов.

Каждый актор, получив сообщение о завершении:
- завершает свою работу;
- вызывает метод акторной системы, удаляющий актор из таблицы.

Когда таблица акторов становится пустой, акторная система завершает свою работу.

19. Игнорирование неизвестных сообщений
Если актор получает сообщение, тип которого ему неизвестен, он игнорирует его (с возможным логированием).
Актор может принимать любые сообщения, но обрабатывает только те, для которых у него определён обработчик.

Это позволяет реализовать версионность акторов: старые реализации могут не знать о новых типах сообщений и продолжать
стабильную работу, а новые реализации обрабатывают расширенный набор. Система эволюционирует плавно, без необходимости
одновременного обновления всех акторов. Актор — это эластичный обработчик: неизвестное не ломает, новое добавляется постепенно.

21. Жизненный цикл актора
Жизненный цикл актора состоит из трёх фаз:

- Создание. В конструкторе актор инициализирует все свои внутренние структуры и очередь сообщений. После создания актор
регистрируется в таблице акторов и готов к приёму сообщений.

- Активная фаза. Основное время жизни актор ожидает сообщения из своей очереди и обрабатывает их последовательно.

- Завершение. Получив стандартное сообщение завершения, актор:
  - аккуратно завершает своё состояние, при необходимости дожидаясь завершения внутренних асинхронных операций или событий;
  - вызывает метод акторной системы, удаляющий его из таблицы акторов;
  - освобождает все занимаемые ресурсы (фактически — аналог Dispose).

После завершения актор не может снова стать активным. Это даёт нам кооперативное и предсказуемое завершение.
Кстати, сообщение завершения — кандидат на одно из фиксированных системных сообщений (как и сообщение об аварийном
завершении системы).

22. Ожидание завершения и кооперативная отмена
Акторная система содержит внутренний TaskCompletionSource, позволяющий внешнему окружению асинхронно дождаться
полного завершения системы (await).

Акторная система предоставляет публичное свойство CancellationToken. Токен переходит в состояние Cancelled после вызова
Panic (аварийное завершение) или Shutdown (завершение). Акторы используют этот токен для кооперативного прерывания
внутренних асинхронных операций при остановке системы.

23. Сервис времени TimeService
Акторная система предоставляет сервис времени — простой объект (не актор), доступный акторам через публичное свойство
акторной системы.

Сервис времени предоставляет:
  - текущее время в UTC — единственный способ получения времени акторами;
  - методы для создания таймаутов и задержек, используемые акторами для реализации тайм-аутных операций.

Назначения сервиса времени:

Подмена времени в тестах. В продакшене сервис предоставляет реальное системное время. В тестовом режиме — виртуальное время,
позволяющее длительные интервалы выполняться мгновенно. Это обеспечивает быстрые и детерминированные юнит-тесты без реальных
задержек.

Универсальный критерий ошибки по таймауту. Акторы используют сервис времени для отслеживания таймаутов (например,
при переподключении). Если действие не выполнено за заданный интервал виртуального времени, оно считается невыполненным
и требует либо повтора, либо другой реакции.

24. Настройки системы (Settings)
Акторная система содержит объект настроек — простой объект (не актор), доступный акторам через публичное свойство акторной
системы.

Назначение объекта настроек:
- хранить параметры конфигурации акторной системы и акторов;
- предоставлять акторам единую точку доступа к настройкам без обращения к статическим классам, переменным окружения или
  файлам конфигурации напрямую.

Объект настроек:
- иммутабелен после инициализации акторной системы — изменения настроек во время работы не допускаются;
- создаётся через DI при старте системы и передаётся в конструктор акторной системы;
- может содержать любые параметры: таймауты, лимиты, флаги режимов (продакшен/тестирование), уровни логирования,
  размеры буферов очередей и т.п.;
- в тестовом окружении может быть заменён на специализированную тестовую конфигурацию.
